# smolvlm profile and optimization on Colab T4 (2026-10-20)

## Setup

| | |
|---|---|
| GPU | NVIDIA Tesla T4 (Colab, 16 GB) |
| torch | 2.9.0+cu128 (Colab preinstalled) |
| baseline commit | `600f8aa` (branch `perf/colab-2x`) |
| optimized commit | `e86a153` (branch `perf/colab-2x`) |
| date | 2026-10-20 |
| model | `HuggingFaceTB/SmolVLM-500M-Instruct` (local snapshot) |
| prompt | "Hello, how are you?" (text only, no image) |
| sampling | `max_tokens=64, temperature=0.0`, dtype `bfloat16` |
| n_runs | 5 timed runs after 1 warmup, wall = median |

Harness: `Omni.generate()` on the Colab VM, one request per call. The
`custom_output["stage_ms"]` split comes from the `profile_range()`
NVTX markers in `models/smolvlm/stage.py`.

## Phase 1 -- baseline profile

`nsys profile --trace=cuda,nvtx` on the baseline commit (report
`/content/nsys_smolvlm.nsys-rep`, 3.7 MB, kept local).

NVTX ranges of the profiled run:

| range | time |
|---|---:|
| `:tokenize` | 11.7 ms |
| `:vlm-prefill` | 370.4 ms |
| `:vlm-decode` | 873.7 ms |

The profiled run has no warmup, so `:vlm-prefill` also carries the
one-off inductor compile of the fork's compiled ops (RMSNorm,
SiluAndMul, rotary, sampler). The timed runs below warm up first.

Top kernels of the whole process:

| kernel | total | calls |
|---|---:|---:|
| `magma_sgemmEx_kernel` | 1029.98 ms | 256 |
| `elementwise_kernel` | 754.12 ms | 5908 |
| `vectorized_elementwise_kernel` | 423.35 ms | 10007 |
| `cunn_SoftMaxForwardReg` | 341.21 ms | 32 |
| `volta_sgemm_128x64_tn` | 321.70 ms | 32 |
| `volta_sgemm_64x64_nn` | 271.47 ms | 32 |

The GEMM kernels are the `volta_sgemm` / `magma_sgemm` family: the
decode model ran in **fp32**, so the T4 used no tensor core. The
`magma_sgemmEx` path is cuBLAS' non-tensor-core fallback.

CUDA API summary of the same run:

| call | total | calls |
|---|---:|---:|
| `cudaLaunchKernel` | 434.30 ms | 23792 |
| `cudaStreamSynchronize` | 34.44 ms | 1000 |

Kernel time 3289.7 ms over a 13572.0 ms span: the GPU was busy **24 %**
of the time. The decode loop is launch-bound, not compute-bound.

## Phase 2 -- two fixes, both measured

**1. The decode model ran in fp32.** `models/smolvlm/stage.py` builds
its own copy of the weights in the requested dtype, but the fork read
the checkpoint dtype from the hub config and built the model that
runs the decode loop in fp32. The stage config mapper now forwards
the dtype (`nanovllm_omni/engine/stage_runner.py`). The wall time on
the T4 does not move; the peak VRAM does (9976 MB -> 7163 MB).

**2. The decode loop ran in eager mode.** The captured graph turns a
decode step into one replay, which removes the launch overhead that
the profile showed. The fork now bounds the captured KV window
(`Config.graph_max_seq_len`), falls back to eager when the context
grows past that window, and falls back to eager when the capture
fails on the device. `models/smolvlm/stage.py` turns the graph on by
default; `extra["use_cuda_graph"] = False` turns it off. This is the
change that carries the speedup.

## Phase 3 -- wall clock

Same host, 5 runs each, median of the wall time. The four cells were
measured in one process (the dtype and the graph are independent
knobs):

| cell | wall p50 | all runs (ms) | peak VRAM |
|---|---:|---|---:|
| fp32 eager | 684.0 ms | 684.0 / 676.5 / 688.0 / 692.8 / 667.3 | 9976 MB |
| bf16 eager | 699.2 ms | 699.2 / 739.5 / 768.7 / 693.8 / 659.8 | 7163 MB |
| fp32 graph | 177.3 ms | 183.0 / 175.7 / 177.3 / 181.7 / 174.4 | -- |
| bf16 graph | **179.0 ms** | 179.0 / 177.6 / 178.3 / 189.9 / 206.7 | 3959.9 MB |

All four cells generate the same text, so neither knob changes the
result.

**The CUDA graph is the whole speedup** (3.8x). The dtype fix does not
change the wall time on the T4 -- fp32 and bf16 decode at the same
speed once the graph removes the launch overhead. What the dtype fix
buys is memory: the peak drops from 9976 MB to 7163 MB, because the
decode model holds its weights in the requested dtype. On a 4 GB card
the fp32 decode model does not fit at all.

End-to-end through `Omni.generate()` on the optimized commit:

| metric | baseline (VM 1) | optimized (VM 2) |
|---|---:|---:|
| wall p50 | 586.0 ms | 185.7 ms |
| stage `vlm` | 585.8 ms | 185.5 ms |
| peak VRAM | 3951.7 MB | 3959.9 MB |
| text | " " | " " |

**3.16x** against the baseline commit, **3.8x** against the eager cell
measured on the same host. The two baseline numbers differ because the
eager path is launch-bound and therefore follows the host CPU speed:
the first baseline ran on a different Colab host than the optimized
run. The same-host comparison is the one to trust.

## Limitations

- The nsys report is a local artifact (`/content/nsys_smolvlm.nsys-rep`).
  Only the conclusions live in this document.
- No ncu run covers the two changes. The ncu counters in
  `docs/adr/0003-profile-results-2026-09-13.md` come from 2026-09-13
  and predate both changes; the T4 stopped handing out sessions after
  the wall-clock runs, so the post-change counters are still open.
- The graph capture was verified on the T4 only. On the RTX 3050 the
  capture used to fail (`cudaErrorStreamCaptureInvalidated`); the fork
  now catches that failure and runs eager, so the 3050 numbers in
  `docs/adr/0003-profile-results-2026-09-13.md` still stand.
- The profile ran without a warmup, so the prefill range carries the
  inductor compile. The wall-clock numbers are warm.
- MiniMind-O and SmolVLA were not measured in this session; see
  `docs/perf/minimind-omni-2026-10-20.md` for the reason and the open
  item.
