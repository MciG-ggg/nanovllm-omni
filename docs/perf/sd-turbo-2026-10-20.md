# sd-turbo profile and optimization on Colab T4 (2026-10-20)

## Setup

| | |
|---|---|
| GPU | NVIDIA Tesla T4 (Colab, 16 GB) |
| torch | 2.9.0+cu128 (Colab preinstalled) |
| baseline commit | `600f8aa` (branch `perf/colab-2x`) |
| optimized commit | `e86a153` (branch `perf/colab-2x`) |
| date | 2026-10-20 |
| model | `stabilityai/sd-turbo` (fp16) |
| prompt | "a photo of a cat" |
| sampling | `num_inference_steps=1`, guidance_scale 0.0, dtype `float16` |
| n_runs | 5 timed runs after 1 warmup, wall = median |

Harness: `Omni.generate()` on the Colab VM. The stage split comes from
the `custom_output["stage_ms"]` marker of the diffusion stage.

## Phase 1 -- where the wall time goes

Per-request breakdown, measured on the pipeline itself (each part
timed separately with a CUDA sync, 8 samples, median):

| part | time |
|---|---:|
| `prepare_encode` (CLIP text encoder + latents) | 20.5 ms |
| `denoise_step` (UNet, 1 step) | 72.9 ms |
| `step_scheduler` (Euler) | 0.7 ms |
| `post_decode` (VAE decode) | 176.3 ms |
| PNG encode of the 512x512 result (default level) | 146.3 ms |
| PNG encode of the same image (level 1) | 34.8 ms |

The two PNG rows are the same pixels with a different zlib level.

## Phase 2 -- cells that were measured and rejected

| cell | result | verdict |
|---|---|---|
| `channels_last` weights and input (whole pipeline) | 427.1 ms vs 284.2 ms | rejected, 1.5x slower |
| `channels_last` VAE only, input in the same layout | 318.8 ms vs 174.8 ms | rejected, 1.8x slower |
| `torch.backends.cudnn.benchmark = True` | 281.0 ms vs 284.2 ms | no measurable change |
| `torch.compile` on the VAE decoder | 159.8 ms vs 174.6 ms, 48 s compile | rejected, 1.09x for a 48 s first call |

The channels-last result is the opposite of the usual advice for
diffusion on tensor-core GPUs: on the T4 the NHWC path costs 1.8x on
the VAE decoder.

## Phase 3 -- the change that paid off

`nanovllm_omni/outputs.py` writes the PNG with `compress_level=1`.
The pixels are the same, the file is a few kilobytes larger, and the
encode drops from 146.3 ms to 34.8 ms on this host.

| metric | baseline | optimized |
|---|---:|---:|
| wall p50 | 377.9 ms | 298.4 ms |
| stage `sd_turbo` | 274.1 ms | 263.5 ms |
| peak VRAM | 3101.0 MB | 3109.1 MB |

**1.27x** end to end. The stage itself did not change; the saving is
in the response path.

## Why 2x is out of reach for this model on a T4

The GPU work of one 512x512 request is the VAE decode (174.3 ms) plus
the UNet step (72.9 ms) = **247 ms**, and no cell above touched that
floor. The remaining 51 ms of the 298 ms wall is the text encoder
(20.5 ms), the Euler step (0.7 ms), and the PNG encode (34.8 ms).

A 2x end-to-end result would need the request to cost about 149 ms,
which the VAE decode alone exceeds. The only lever left is the output
resolution: 256x256 cuts both the UNet and the VAE by about 4x. That
changes the delivered image, so it is a contract decision, not an
optimization, and it was not applied.

## Limitations

- The `channels_last` and `torch.compile` cells ran on the pipeline
  directly, not through `Omni.generate()`. The PNG cell ran through
  the full path.
- The baseline and the optimized run used two different Colab hosts.
  The PNG encode is CPU bound, so the two hosts disagree on its cost
  (the same encode cost 146.3 ms in isolation and about 104 ms inside
  the baseline request). The 1.27x number is therefore the
  conservative one.
- The diffusers version is 0.41.0; the VAE runs in fp16 because the
  stage calls `vae.decode` directly and never goes through the
  pipeline-level upcast.
