## Per-input scaling observation

- **short (123 ms)**: p99/p50 ratio 1.30 -- high variance. The first forward is ~160 ms (cuDNN/cuBLAS heuristic compile + lazy CUDA init); subsequent forwards settle near 110 ms.
- **medium (3905 ms)**: ratio 1.06. Variance dominated by AR token sampling decisions (some tokens take longer to process due to logits sorting).
- **long (3969 ms)**: ratio 1.05. Same as medium -- prompt-length effect (~25 vs ~80 tok) is amortized over 64 AR tokens; the LM forward cost per AR token is the dominant cost regardless of input.

## Implied AR decode cost

Subtracting short from medium (which differ only in prompt size, not max_new_tokens):
- short: 123 ms (prefill 10 tok + decode 64 tok)
- medium: 3905 ms (prefill 25 tok + decode 64 tok)
- long: 3969 ms (prefill 80 tok + decode 64 tok)

Difference (medium - short) = 3782 ms attributed to ~15 extra prefill tokens. That's ~250 ms / prefill token, vs decode at ~60 ms / token (123 ms total / ~64 decode tokens ~= 1.9 ms/decode). Wait, that doesn't add up -- let me recompute.

Pre-fill cost for short = prefill(10) + decode(64) = 123 ms. Pre-fill cost for medium = prefill(25) + decode(64) = 3905 ms. Difference = 15 prefill tokens = 3782 ms = **252 ms / prefill token**.

Compare decode cost: 64 decode tokens / 123 ms ~= 1.9 ms / decode token (short prompt).
64 decode tokens / 3905 ms ~= 61 ms / decode token (medium prompt).

The decode-token cost varies wildly by prompt length. That's the SMoLLM vision encoder + chat template overhead -- each decode forward passes through SigLIP vision for the chat template image blocks (even with images=[]).

Actually for text-only the vision encoder should be a no-op. The 61 ms/decode token suggests something else is happening per decode step. Need per-stage NVTX to confirm. Phase 2 follow-up.

## Peak VRAM

~1000 MiB for all 3 inputs. This is the BF16 SmolVLM-500M model footprint (1 GB BF16 ~= 500M params * 2 bytes). KV cache + intermediates contribute negligibly at this scale.

Headroom for larger max_new_tokens: 4096 - 1000 = ~3000 MiB available. Could comfortably push max_new_tokens to 256-512 without OOM.
